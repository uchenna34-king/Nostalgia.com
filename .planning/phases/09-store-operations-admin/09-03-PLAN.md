<objective>
Stand up the owner-gated admin shell and dashboard: the `/admin` route section with its own layout/nav (D-14), gated at the top by `requireOwner()` (delivered in 09-02), rendered in the locked "nostalgic luxury streetwear" design system but as a denser back-office surface — explicitly WITHOUT the storefront film-grain overlay and WITHOUT the marquee. This is the first admin screen a signed-in owner sees; later plans (09-04 product/collection CRUD, 09-06 orders) hang their pages under this shell.

Implements ADMN-01 (admin-gated dashboard) and D-14 (own `/admin` route section, own layout/nav, on-brand back-office).

Purpose: give the owner a real entry point and navigation chrome for the no-code admin, and lock in the visual + authorization contract every later admin page inherits. The layout's `requireOwner()` call is the RENDERING gate for all admin pages; mutations built later must still guard themselves (carried forward from 09-02).

Output: `app/admin/layout.tsx` (shell + owner gate), `components/admin/AdminNav.tsx` (section nav), and `app/admin/page.tsx` (dashboard landing with real counts + quick links).
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous/authenticated browser → `/admin` + `/admin/*` page rendering | A visitor requests the admin dashboard/section pages; rendering must be gated by the layout before any admin chrome or data renders. |
| `session.user.email` (JWT claim) → owner decision | The layout's `requireOwner()` uses the session email as the sole authorization input; validated server-side per request via the 09-02 helper. |
| admin Server Action / Route Handler → (built in 09-04/09-06) | Out of this plan's scope, but the layout guard explicitly does NOT cover these; recorded here so the contract is not lost. |

## STRIDE Threat Register (ASVS L1 — block on high)

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-05 | Elevation of Privilege | non-owner / anonymous visitor reaches admin page rendering (`app/admin/layout.tsx` + children) | high | mitigate | `app/admin/layout.tsx` calls `await requireOwner()` as its FIRST statement: anonymous → redirect to /signin, authenticated non-owner → notFound(). Server-side, never UI-hiding. Ordering enforced per RESEARCH Pitfall 2 so the gate fires before the 200 status locks. |
| T-09-06 | Information Disclosure | admin existence / structure revealed to a non-owner via error text, nav, or dashboard | medium | mitigate | `requireOwner()` returns a plain 404 (notFound()) for authenticated non-owners rather than a 403, so the admin's existence is never confirmed; AdminNav and the dashboard only render inside the gated layout subtree, so no admin structure leaks to non-owners. |
| T-09-07 | Elevation of Privilege | admin Server Action / Route Handler (09-04/09-06) invoked directly, bypassing the layout gate | high | mitigate (deferred) | This plan introduces NO mutations, so no unguarded action ships here. The binding contract — every admin Server Action / Route Handler calls `requireOwner()` as its FIRST line — is carried in `must_haves.prohibitions`, the layout's doc comment, and inherited from 09-02 (T-09-01). The layout rendering-guard is explicitly documented as NOT sufficient for those endpoints. |

Both high-severity threats in scope (T-09-05) and the carried-forward contract (T-09-07) are mitigated; T-09-06 (medium) is mitigated by the notFound()-not-403 behavior.
