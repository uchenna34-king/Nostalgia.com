# Phase 11 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope reminder:** This phase is infrastructure-first. New UI surface is deliberately small — an order list on `/account`, an order detail page at `/account/orders/[id]`, an order confirmation email, and light touch-ups to `/order/success` and `/signin`. No storefront, cart, checkout, admin, or PDP redesign. Do not add UI beyond what's specified here.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | none (hand-rolled Tailwind utilities + a small set of `@layer components` classes) |
| Icon library | none — inline SVG only (see `components/SignInForm.tsx`'s Google mark); no icon-font/icon-package dependency exists in the project |
| Font | Fraunces (serif, display/headings) + Inter (sans, body) — both loaded as CSS variables (`--font-fraunces`, `--font-inter`) and mapped in `tailwind.config.ts` |

**Why no shadcn:** `components.json` does not exist anywhere in this codebase (confirmed by directory scan). Nostalgia has a fully locked, hand-built design system in place since Phase 1 (`app/globals.css` `@layer components`: `.btn-primary`, `.btn-outline`, `.eyebrow`, `.container-x`, `.link-underline`) that every prior phase (3–10) has extended rather than replaced. Introducing a component library one phase before production cutover would contradict D-11/D-12's "no last-minute surprises" framing and add churn with zero benefit to this phase's four small UI additions. Registry safety gate: not applicable.

## Spacing Scale

Declared values (must be multiples of 4), already in active use across the codebase (`py-16`, `gap-3`, `mt-10`, `px-5`, etc.):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps, tight inline padding |
| sm | 8px | Compact spacing (status pill `px-2 py-1`, form label-to-input gap) |
| md | 16px | Default element spacing (card padding, gap between stacked rows) |
| lg | 24px | Section padding, gap between order list rows on mobile cards |
| xl | 32px | Layout gaps (space between page header and content body) |
| 2xl | 48px | Major section breaks (`mt-10` region between hero copy and CTA row, matches `/account`'s existing rhythm) |
| 3xl | 64px | Page-level vertical padding (`py-16`, matches `/account`, `/wishlist` top-level `<main>` padding) |

Exceptions: none. Reuse the page-level padding already established by `/account` (`container-x py-16`) for both new/restructured account routes; reuse `/admin/orders/[id]`'s `max-w-3xl` content width for `/account/orders/[id]` (narrower than the full `container-x` width, appropriate for a single-column receipt-style layout).

## Typography

Declared for phase 11's new/touched UI (mirrors the sizes and weights already established site-wide — do not introduce new sizes):

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label / eyebrow | 12px (`text-xs`) | 400 regular, `uppercase tracking-[0.25em]` (via `.eyebrow`) or `tracking-[0.15em]`/`[0.18em]` for table headers and secondary labels | 1.4 |
| Body | 14px (`text-sm`) | 400 regular | 1.5 |
| Section heading | 18–20px (`text-lg`/`text-xl`) | 400 regular (Fraunces default) | 1.3 |
| Page heading (sub-page, e.g. order detail) | 30px (`text-3xl`) | 400 regular (Fraunces default) — matches `app/admin/orders/[id]/page.tsx`'s existing `h1` exactly | 1.2 |
| Display heading (top-level account page) | 48px (`text-5xl`) | 900 (`font-black`) — matches `/account`'s and `/order/success`'s existing `h1` exactly | 1.1 |

**Weight declaration (2 weights for new interactive/body elements):** Regular 400 (serif section/page headings, all body copy) and Medium 500 (`font-medium` — table headers, status pills, buttons, "View order" links). `font-black` (900) is reserved exclusively for the single top-level `<h1>` per page (already the sitewide convention since Phase 1 — not a new rule introduced here).

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `cream` `#F4EEE4` | Page background for `/account`, `/account/orders/[id]`, `/signin` |
| Secondary (30%) | `cream-dark` `#E8DFCF` | Table zebra dividers (`border-cream-dark`), empty-state card background, mobile order-card background, table header rule |
| Accent (10%) | `sepia` `#A6552F` on cream backgrounds only where AA-safe; `sepia-deep` `#8A4524` wherever the accent sits directly on `cream-dark` or inside a tinted pill on `cream`/`cream-dark` | Order id links (`#{ref}` → order detail), "View order" links, focus-visible ring (inherited from global `:focus-visible`), primary CTA hover states, the "paid" status pill's text |
| Destructive | `#9B2C2C` (existing token used by `OrderTable`'s cancelled pill — reuse exactly, do not introduce a new red) | "Cancelled" status pill only |

**Accent reserved for:** order reference links (`#{orderId.slice(-8)}` on the order list), the "View order" affordance, hover state on `.btn-primary`/`.btn-outline`, the "paid" status pill, and the global focus ring. Never apply sepia/sepia-deep to the "pending" or "fulfilled" pills (see Status Presentation below) — those use neutral ink/cream-dark and solid ink respectively, so the accent's meaning ("action" / "in-progress-positive") stays legible and distinct.

**Locked AA rule (carried forward from Phase 10, restated for this phase):** raw `sepia` measures below 4.5:1 on `cream-dark` and on `ink`. Any sepia-toned text or pill introduced in this phase that sits on `cream-dark` (table zebra rows, mobile order cards) or inside a tinted pill background must use `sepia-deep`, never raw `sepia`. This directly affects the "paid" status pill spec below, which deliberately deviates from `components/admin/OrderTable.tsx`'s existing `pillClass` (which uses raw `text-sepia` on `bg-sepia/15` — acceptable there only because that table's rows sit on plain `cream`, not `cream-dark`; do not copy that exact class string into a context where the row background is `cream-dark`).

## Specific Contracts (Phase 11)

### 1. Empty state — signed-in customer, zero orders

Render inside the restructured `/account` page (Server Component), below the existing "Hello, {name}" greeting block — do not replace the greeting. Use the same visual language as `components/admin/OrderTable.tsx`'s existing empty state (a `cream-dark` card, not a full-page empty state like `/wishlist`'s, since `/account` already has content above it):

```
<div class="mt-10 rounded-sm bg-cream-dark px-6 py-16 text-center">
  <h2 class="font-serif text-xl text-ink">No orders yet</h2>
  <p class="mt-2 text-sm text-ink-soft">When you place an order, it'll show up here.</p>
  <Link class="btn-primary mt-6">Browse the collection</Link>
</div>
```

Heading level: `<h2>` (the page's `<h1>` is "Hello, {name}"; do not skip to a bare unlabeled block — matches the Phase 10 precedent of using explicit heading levels for screen-reader structure).

### 2. Status presentation — four `ORDER_STATUSES`, color + text paired (WCAG 1.4.1)

All four states are always rendered with a visible text label alongside color — never color alone. This is a 4-state customer-facing view, so it deliberately extends (not copies verbatim) `OrderTable.tsx`'s 3-bucket admin scheme, which only distinguishes `fulfilled`/`cancelled`/other:

| Status | Label (exact string) | Classes | Rationale |
|--------|----------------------|---------|-----------|
| `pending` | "Pending" | `bg-cream-dark text-ink-soft` | Neutral — order placed, payment not yet confirmed. |
| `paid` | "Paid" | `bg-sepia-deep/12 text-sepia-deep` | Accent-tinted — positive, in-progress. Uses `sepia-deep` (not raw `sepia`) because this pill can appear on a `cream-dark` mobile-card background (see Responsive below) — must clear 4.5:1 in both contexts. |
| `fulfilled` | "Fulfilled" | `bg-ink text-cream` | Solid — most emphatic, signals the order is complete/shipped. Intentionally the strongest visual weight of the four. |
| `cancelled` | "Cancelled" | `bg-[#9B2C2C]/10 text-[#9B2C2C]` | Destructive tint — reused verbatim from `OrderTable.tsx`'s existing cancelled treatment. |

Pill markup: `<span class="inline-block rounded-sm px-2 py-1 text-xs font-medium">{label}</span>` — same shape as the admin table's pill, `font-medium` added for slightly stronger legibility at 12px since this is customer-facing.

### 3. Order reference display

Consistent everywhere an order is referenced: `#{orderId.slice(-8)}` — exact same slice already used on `/order/success` and `app/admin/orders/[id]/page.tsx`. Do not introduce a different truncation length or a different prefix character. No `tabular-nums` (the id is an alphanumeric cuid fragment, not a number — `tabular-nums` is reserved for prices/quantities per existing convention).

### 4. Not-found / not-yours — `/account/orders/[id]`

Query must be scoped by both `id` AND `userId` in a single `findFirst` (not `findUnique` + a separate ownership check) so a non-owner and a non-existent id are indistinguishable at the data layer. On no match, call `notFound()` and let the existing branded `app/not-found.tsx` render (see Copywriting Contract above) — no bespoke messaging, no distinct "this isn't your order" state. This mirrors `lib/admin.ts`'s established precedent of never revealing existence.

### 5. Responsive — order list degrades without horizontal page scroll

- **≥640px (`sm:` and up):** render as a `<table>`, directly mirroring `components/admin/OrderTable.tsx`'s markup and column set — `Order | Date | Items | Total | Status`. Every cell text-sm, header row `text-xs uppercase tracking-[0.15em] text-ink-soft border-b border-cream-dark`.
- **<640px:** do not render the `<table>` element at all (not `overflow-x-auto` — that still allows horizontal scroll, which is explicitly disallowed). Render a stacked list of `cream-dark` cards instead, one per order, each with:
  - Row 1: order reference (sepia-deep link) on the left, date on the right (`text-ink-soft`)
  - Row 2: status pill on the left, total on the right (`tabular-nums`)
  - Entire card wrapped in the "View order" link/`<Link>` for a larger tap target (44px minimum height per the existing icon-touch-target exception), with the same `aria-label` pattern as the table row.
  - Vertical gap between cards: 16px (`gap-4` / `space-y-4`).
- Implementation note: use Tailwind's responsive prefixes to swap between the two markup structures (`hidden sm:block` on the table, `sm:hidden` on the card list) rather than CSS-only reflow, since a `<table>` cannot reasonably reflow into cards with pure CSS while keeping semantic table markup intact for the desktop view.

### 6. Email template constraints — `emails/OrderConfirmation.tsx`

Hard constraints, because most email clients (Outlook desktop in particular) do not support modern CSS, flexbox/grid, or web fonts:

- **Layout:** table-based only, via React Email's `Section`/`Row`/`Column` primitives (which render as HTML tables under the hood) — never a flex/grid `div` structure.
- **Styling:** inline styles only (React Email components accept a `style` prop that inlines automatically) — no `<style>` block, no Tailwind classes (Tailwind's utility classes do not exist in the rendered email HTML).
- **Fonts — no web fonts will load in Gmail/Outlook.** Use the exact fallback chain already declared in `tailwind.config.ts` so the email at least degrades to the same fallback the app itself would use if Fraunces/Inter failed to load:
  - Headings: `font-family: Georgia, 'Times New Roman', serif` (matches `fontFamily.serif`'s documented fallback, minus the unavailable `var(--font-fraunces)`).
  - Body: `font-family: -apple-system, BlinkMacSystemFont, 'Segoe UI', Helvetica, Arial, sans-serif` (standard email-safe sans stack; matches the spirit of `fontFamily.sans`'s `system-ui` fallback).
- **Colors:** hex values only, exactly `cream` `#F4EEE4`, `ink` `#1A1A1A`, `sepia-deep` `#8A4524`. Use **`sepia-deep`, not raw `sepia`**, for any accent text or link in the email — Outlook and most email clients render on a plain white or light background by default (not `cream-dark`), and raw sepia's contrast margin is thin enough (4.59:1 on cream in the app's own measured data) that it should not be risked in an environment this project cannot visually QA per-client. Order status pills inside the email reuse the same four-state palette as Contract #2, but rendered as plain colored text (no rounded-pill `<span>` background — background-color support on inline elements is inconsistent across email clients; a bold color-coded word is more reliable than a styled badge).
- **Width:** fixed 600px max content width, centered, standard email convention.
- **Images:** product thumbnails (if included) must have explicit `width`/`height` attributes and an `alt` attribute (many clients block remote images by default; alt text is the fallback).
- **Plain-text alternative:** required. Use React Email's `render(<OrderConfirmationEmail ... />, { plainText: true })` (or Resend's own plain-text generation if it wraps this) to generate the text part — do not hand-write a separate plain-text template that could drift from the HTML one.
- **Preheader:** include a hidden preview-text block (React Email's `Preview` component) so inbox previews show something meaningful ("Your Nostalgia order #{ref} is confirmed") rather than raw HTML/whitespace.
- **Content scope:** order reference (`#{ref}`, same slice convention as Contract #3), line items (name, size, qty, unit price, image if available — via `parseOrderItems`), order total, and — per D-06a — no promise of a specific delivery timeline beyond what `/order/success` already states, since real shipping/returns copy is explicitly deferred (D-12).

### 7. `/order/success` — optional "confirming payment…" state (Claude's discretion, D-04)

D-04 selected webhook-only confirmation; the success page stays presentational by default. If a transient "confirming payment…" state is added (only if low-cost), it must:
- Not block or delay the existing cart-clearing/analytics `useEffect`s.
- Use the same `.eyebrow` + `text-ink-soft` treatment as the rest of the page, not a spinner/loading pattern borrowed from elsewhere.
- Never claim the payment failed if the webhook simply hasn't arrived yet — the copy must stay neutral ("Confirming your payment…") rather than implying doubt.
- This is optional; if omitted, no visual contract violation occurs — the page's existing content (order reference, "Thank you.", CTAs) already satisfies LIVE-02/LIVE-03's UI needs.

### 8. `/signin` — one-provider vs. two-provider layout (`ALLOW_DEMO_LOGIN`)

The page must look complete and intentional in both configurations, not like a component failed to render:

- **Two providers (UAT: Google + Demo, `ALLOW_DEMO_LOGIN=true`):** Google button first (primary, `border-ink` outline style, unchanged from current `components/SignInForm.tsx`), then a centered "or" divider (`text-xs text-ink-soft`, `my-4`, flanked by two thin `border-cream-dark` horizontal rules spanning the remaining width), then the demo email input + "Sign in as store owner" button beneath it — same visual weight as today's dev-fallback block, just re-labeled as "Demo login (for testers)" rather than "Dev mode" copy (since this now runs on a public UAT URL, not only `localhost`).
- **One provider (go-live: Google only, `ALLOW_DEMO_LOGIN=false`):** render only the Google button, centered in the same `max-w-sm` container, with no divider, no empty space reserved for the removed block, and no leftover "Dev mode" copy beneath it. The button's own `mt-10` spacing from the page heading (already established) is sufficient — do not add extra vertical centering hacks to "fill" the space.
- Both states reuse the exact same Google button markup/copy ("Continue with Google") — do not fork that component's core button between states.
