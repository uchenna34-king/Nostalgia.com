  <action>
    Create `app/product/[slug]/actions.ts` as a `"use server"` module exporting
    `async submitReview(formData: FormData): Promise<ReviewActionResult>`, where
    `ReviewActionResult = { ok: true } | { ok: false; error: string }` (mirror `ProductActionResult`).

    As the FIRST statements — mirroring `requireOwner()`'s gate discipline — call
    `getServerSession(authOptions)`, read `userId` via `(session?.user as { id?: string })?.id`.
    If there is no `userId`, return `{ ok: false, error: "not_authenticated" }`. Never read or
    trust any client-asserted eligibility value (D-01, threat T-10-05-01).

    Extract fields explicitly with a trim helper (like `field()` in the admin actions — never
    spread FormData into Prisma `data`): `slug` (from a hidden field), `rating` (via `Number`),
    `title`, `body`.

    Validate in this order, returning a distinct error string per failure:
    - `isValidRating(rating)` (imported from `@/lib/reviews`) — the 1-5 allow-list clamp; on
      failure return `"invalid_rating"` (threat T-10-05-02).
    - Require a non-empty trimmed `title`; if blank return `"missing_title"` (D-03: title
      required, body optional).
    - Length-cap BEFORE persist: `title.slice(0, TITLE_MAX)` with `TITLE_MAX = 120`;
      `body.slice(0, BODY_MAX)` with `BODY_MAX = 2000`; treat an empty body as `null`
      (threat T-10-05-04).
    - Re-check purchase eligibility server-side: `await hasPurchased(userId, slug)`; if it
      returns false, return `"not_eligible"` (D-01, T-10-05-01). This re-runs on every submit
      and is never cached client-side.

    Resolve the product id: `prisma.product.findUnique({ where: { slug }, select: { id: true } })`;
    if null return `"product_not_found"`.

    Persist with `prisma.review.upsert({ where: { productId_userId: { productId, userId } },
    update: { rating, title, body }, create: { productId, userId, rating, title, body } })`. The
    compound-unique key makes one-review-per-user structural (D-01, T-10-05-03); upsert edits in
    place on resubmit, preserving `id`/`createdAt`. Do the upsert inline in the action (not via a
    lib helper) so the security-critical write stays auditable next to its gate, matching the
    admin actions convention.

    After the write, refresh every surface a rating change affects — copy the targets from the
    admin `revalidateStorefront`: `revalidatePath("/product/[slug]", "page")`,
    `revalidatePath("/shop")`, `revalidatePath("/")`, and
    `revalidatePath("/collections/[slug]", "page")` (D-04, Pitfall 3). Return `{ ok: true }`.

    Import ONLY `hasPurchased` and `isValidRating` from `@/lib/reviews`; import
    `getServerSession`, `authOptions`, `prisma`, and `revalidatePath` directly. No moderation
    logic here — hide/delete is 10-06.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `submitReview` Server Action | Server Actions are independently-callable public HTTP endpoints; all form input and any client-side "eligible" state crossing here is untrusted. |
| stored review text → PDP render (10-04) | Persisted title/body flows back to the review list; treated as untrusted content on render. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-10-05-01 | Tampering / Elevation | submitReview | high | mitigate | Re-run `getServerSession` + `hasPurchased(userId, slug)` as the action's first lines; return `not_authenticated`/`not_eligible` and write nothing. Client eligibility is display-only and never trusted (mirrors `requireOwner()` discipline). |
| T-10-05-02 | Tampering / Input Validation | submitReview | medium | mitigate | `isValidRating` 1-5 allow-list clamp before persist; reject with `invalid_rating`. Fields extracted individually — FormData is never spread into Prisma `data`. |
| T-10-05-03 | Tampering (review spam / duplicates) | Review write | medium | mitigate | DB `@@unique([productId, userId])` + `upsert` make more-than-one-review-per-user structurally impossible, not just app-enforced. |
| T-10-05-04 | Denial of Service (oversized payload) | submitReview | low | mitigate | Length-cap title (120) and body (2000) server-side before persist; empty body stored as `null`. |
| T-10-05-05 | Tampering (stored XSS via review body) | ReviewList render (10-04) | low | accept | Review text renders as React text nodes (auto-escaped, no `dangerouslySetInnerHTML`); length-cap bounds payload. No script-context injection surface in this plan. |

**No package installs in this plan** — `jest-axe` (10-01) and `@vercel/analytics` (10-09) own their legitimacy gates; no `T-{phase}-SC` applies here.
</threat_model>
