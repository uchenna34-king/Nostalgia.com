## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Stripe -> `/api/stripe/webhook` | Untrusted inbound HTTP. Authenticity is established ONLY by the HMAC signature over the raw body; without it, anyone who can reach the URL could post a forged event. |
| webhook payload -> Order lookup | Only `metadata.orderId` is consumed from the event. Every order fact (email, total, current status) comes from the database row, never from the payload. |
| webhook -> `sendOrderConfirmation` | Only an order id crosses; the recipient and content are derived server-side from the looked-up row (11-04's boundary). |
| client -> checkout redirect origin | The redirect origin must come from server config (`NEXTAUTH_URL`), never from a client-forgeable `Origin` header or a hardcoded fallback. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-11-05-01 | Spoofing | Forged webhook marks arbitrary orders paid | critical | mitigate | Every event is verified with `stripe.webhooks.constructEvent(rawBody, signature, STRIPE_WEBHOOK_SECRET)` before any database access; a throw returns 400 with zero writes, and a missing `stripe-signature` header returns 400. Tested by a `constructEvent`-throws case asserting 400 + no `prisma.order.update`. |
| T-11-05-02 | Tampering | Signature bypass via body re-serialization | high | mitigate | The handler reads the RAW body with `req.text()` and passes that exact string to `constructEvent`; it never calls `req.json()` first (Pitfall 1). Asserted by a test that the value verified is byte-for-byte the raw body string, plus a positive grep for `req.text()`. |
| T-11-05-03 | Repudiation | Replayed/duplicate Stripe delivery double-flips status and double-sends email | high | mitigate | The transition runs only when `order.status === "pending"`; any non-pending order is a no-op. A repeated delivery therefore writes nothing and sends no second email — no ledger table needed for this single one-way transition. Tested by an already-`paid` delivery asserting no update and no email. |
| T-11-05-04 | Tampering | Trusting payload contents (amount, email) instead of the stored order | high | mitigate | Only `metadata.orderId` is read from the verified event; the Order row is the sole authority for recipient and total, and this plan adds no write path from the payload into the order. `sendOrderConfirmation` (11-04) derives the recipient from the row's own `email` column, so a payload-supplied address cannot redirect a receipt. |
