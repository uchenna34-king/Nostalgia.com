Output: One tiny new client island (`ViewProductTracker`) plus `trackEvent()` calls added at four existing surfaces.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → Vercel Analytics collector | Event payloads leave the browser for an external service; anything placed in a `trackEvent` payload could be recorded off-platform. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-10-10-01 | Information Disclosure | `trackEvent` payloads at all 5 call sites | medium | mitigate | Restrict every payload to the whitelisted non-PII fields (`productSlug`, `size`, `itemCount`, `amount`, `orderId` as opaque transaction ref, `demo`, `query`). Never pass `email`/`userId`/`session`/customer `name`. Enforced by per-call-site acceptance criteria that inspect the exact argument object (NOT a file-wide grep — `checkout/page.tsx` and `AddToCart.tsx` legitimately reference `user.email`/`product.name` elsewhere, so a blanket negative grep would false-positive). |
| T-10-10-02 | Tampering | client-supplied search term reaching analytics | low | accept | The `search` `query` is user-entered free text; it is the canonical `search_term` for this event and carries no identity binding. No server trust is placed in it (analytics is fire-and-forget); `trackEvent` swallows errors, so a malformed term cannot break the app. |

No package-manager installs occur in this plan (all Phase 10 installs land in 10-01/10-09), so no `T-10-10-SC` package-legitimacy checkpoint is required here.
</threat_model>
