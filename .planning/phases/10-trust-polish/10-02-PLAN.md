<objective>
Establish the persistence foundation for reviews & ratings (TRST-01): add a relational `Review`
model to the Prisma schema, ship an explicit, non-interactive migration for it, and seed sample
"verified purchase" reviews backed by real paid orders.

Purpose: Every downstream reviews plan (10-03 query layer, 10-04 read UI, 10-05 write, 10-06 admin
moderation, 10-11 JSON-LD aggregateRating) reads from this table. Nothing may read reviews before
this plan lands. This is the single schema/migration/seed root for the whole reviews vertical.

Output: `Review` model + back-relations in `prisma/schema.prisma`; a `add-reviews` migration under
`prisma/migrations/`; an updated `prisma/seed.ts` that inserts reviewer users, paid/fulfilled orders,
and verified-purchase reviews, guarded by a seed-time invariant so `npm run seed` exiting 0 is proof
the fixtures are genuinely verified purchases.
</objective>

  <action>
    Ship the Review table as an explicit, dev-runnable, non-interactive Prisma migration. Because the
    project has been on `prisma db push` (there is no `prisma/migrations/` folder and no
    `_prisma_migrations` table), running `prisma migrate dev` cold would detect drift and
    interactively prompt to reset — which violates the non-interactive constraint. Prevent this by
    first baselining the pre-Review database, then generating a clean Review-only diff:

    Step A (baseline the existing db-push schema): create the folder `prisma/migrations/0_init/` and
    write its `migration.sql` from the CURRENT live database (which still lacks the Review table,
    since Task 1 only edited the schema file) using `npx prisma migrate diff --from-empty
    --to-schema-datasource prisma/schema.prisma --script`. This introspects the actual database at the
    datasource URL, so `0_init` captures the pre-Review schema regardless of the edited schema file.
    Then mark it applied without re-running it: `npx prisma migrate resolve --applied 0_init` (the
    tables already exist from db push, so this only records history).

    Step B (generate + apply the Review migration): run `npx prisma migrate dev --name add-reviews`.
    With `0_init` recorded, Prisma diffs the datamodel (now with Review) against migration history
    (pre-Review) and emits a migration containing ONLY the `CREATE TABLE "Review"` plus its indexes
    and unique constraint, applies it to the dev database, and regenerates the Prisma Client. Note:
    `migrate dev` will auto-run the configured seed (`prisma.seed`) afterward — that is expected and
    harmless (Task 3 updates the seed).

    Fallback (only if Step B still reports drift or tries to prompt): the SQLite dev database is fully
    reseedable, so delete the dev database file referenced by `DATABASE_URL` (the `.db` file plus any
    `-journal`/`-wal` siblings), then re-run `npx prisma migrate dev --name add-reviews`. With the
    `_prisma_migrations` table gone, Prisma re-applies `0_init` then `add-reviews` to a fresh database
    with no drift — still non-interactive, and `add-reviews` still contains only the Review table. Do
    NOT hardcode the db path; derive it from `DATABASE_URL`.

    Verify the schema shape is Postgres-portable: the migration SQL must contain only standard DDL
    (CREATE TABLE, CREATE UNIQUE INDEX / CREATE INDEX) with no SQLite-only pragmas beyond what Prisma
    normally emits.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| app write path → database | Later plans (10-05 submit, 10-06 moderation) write reviews across this boundary; the DB-level constraints defined here are the structural gate. |
| seed script → database | Fixture data must not fabricate "Verified purchase" trust signals that no real order backs. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-10-01 | Tampering | Review write path | high | mitigate | `@@unique([productId, userId])` makes more-than-one-review-per-user structurally impossible at the DB level (not just app logic) — the same race-free pattern proven by `ProductSizeStock`. |
| T-10-02 | Integrity / Repudiation | Review FK lifecycle | medium | mitigate | `onDelete: Cascade` on both `productId` and `userId` FKs prevents orphaned reviews when a product is deleted (admin) or a user is removed. |
| T-10-03 | Information Disclosure (false trust) | seed fixtures | medium | mitigate | Seed invariant asserts every seeded review is backed by a `paid`/`fulfilled` order whose items contain the reviewed slug — `npm run seed` cannot exit 0 with a fabricated verified-purchase review. |
| T-10-SC | Tampering | npm/pip/cargo installs | low | accept | This plan performs NO package-manager installs (jest-axe → 10-01, `@vercel/*` → 10-09, the SUS `lighthouse` gate → 10-12). Nothing to gate here. |
</threat_model>
