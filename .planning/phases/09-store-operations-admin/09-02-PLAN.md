<objective>
Establish the phase's authorization boundary: a single reusable server-side owner-email gate plus a first-layer route-matching block, before any admin UI or CRUD exists. This plan delivers the security contract that all downstream admin plans (09-03 layout, 09-04 product/collection CRUD, 09-06 orders) inherit and MUST honor.

Implements D-01 (OWNER_EMAIL env var, placeholder default, no hardcoded real email), D-02 (real server-side owner check via session-email comparison; non-owner hard-blocked), and D-03 (single-owner-by-email — no User.role field).

Purpose: Everything before Phase 9 was public or "any authenticated user." This is the project's first authorization surface. Getting the gate right here means downstream CRUD/order plans just call one helper and cannot accidentally ship an unprotected admin mutation.

Output: `lib/admin.ts` (OWNER_EMAIL, isOwnerEmail, requireOwner), `middleware.ts` (first-layer /admin block), `tests/admin.test.ts`, and an OWNER_EMAIL entry in `.env.example` / `.env`.

Dev note: the owner tests locally by signing in through the existing dev-demo credentials provider (`lib/auth.ts`, id "demo") using the `OWNER_EMAIL` address. No change to `lib/auth.ts` is required this phase — the demo provider already upserts a User for any typed email (RESEARCH Open Question 3).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous/authenticated browser → `/admin/*` routes | Untrusted visitor attempts to reach admin pages; must be gated before any admin data renders. |
| direct HTTP client → admin Server Action / Route Handler | Server Actions are public POST endpoints callable directly (e.g. curl with a session cookie), bypassing the rendered UI and the layout — the primary abuse surface this plan's contract addresses. |
| `session.user.email` (JWT claim) → owner decision | The email string from the NextAuth JWT session is the sole input to the authorization decision; its presence and value must be validated server-side per request. |

## STRIDE Threat Register (ASVS L1 — block on high)

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-01 | Elevation of Privilege | admin Server Actions / Route Handlers (built in 09-04/09-06) invoked directly, bypassing UI + layout | high | mitigate | `requireOwner()` (Task 1) is the single reusable gate; its doc comment and this plan's `must_haves.prohibitions` establish the binding contract that every admin action/route calls it as its FIRST line. Server Actions have zero built-in authorization (RESEARCH Pattern 1 / Pitfall 1). |
| T-09-02 | Elevation of Privilege | non-owner authenticated session reaches admin routes | high | mitigate | `requireOwner()` (Task 1) compares `session.user.email` to `OWNER_EMAIL` server-side and calls `notFound()` for non-owners; `middleware.ts` (Task 2) adds a first-layer anonymous redirect. Block is server-side, never UI-hiding. |
| T-09-03 | Spoofing | missing `session.user.email` / `session.user.id` treated as authorized | high | mitigate | `requireOwner()` (Task 1) explicitly guards on `session?.user?.email` presence and `redirect()`s to sign-in when absent, before any owner comparison — no null/undefined email path can pass the gate. |
| T-09-04 | Spoofing | owner-email spoofing via the dev-demo credentials provider (accepts any typed email) | low | accept | Accepted for local dev only (the demo provider is how the owner tests locally per D-02). Mitigated at Phase 11 go-live by real Google OAuth + the real `OWNER_EMAIL` in `.env`; no source change needed now (RESEARCH Open Question 3). Documented, not code-fixed this phase. |

**Note (supply chain):** This plan installs no packages (`next-auth` and `next` are already installed and audited) — no `T-09-SC` install checkpoint applies. All three high-severity threats are mitigated by Task 1 (the `requireOwner` helper and its contract); no high threat is left unmitigated.
