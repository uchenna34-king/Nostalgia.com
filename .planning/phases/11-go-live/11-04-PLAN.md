<objective>
Deliver the order confirmation email capability for LIVE-03: install the Resend + React Email
dependencies behind a blocking package-legitimacy checkpoint, build the
`emails/OrderConfirmation.tsx` template to 11-UI-SPEC.md's email constraints, and expose
the single shared `sendOrderConfirmation(orderId)` function that D-06 requires.

Purpose: today nothing in this repo can send mail — `/order/success` promises "We'll send a
confirmation shortly" and that promise is a lie. D-05 selects Resend with React Email so the
receipt carries the Nostalgia palette rather than generic system styling. D-06 requires ONE
function called from both the real Stripe webhook and the demo/stub checkout branch, so UAT
testers exercise the identical send path a paying customer will.

Output: a working, unit-tested `sendOrderConfirmation(orderId)` that is a safe no-op when
`RESEND_API_KEY` is absent, and a branded email template that survives Outlook and Gmail.

Scope fence: this plan EXPOSES the function. It does not call it. Plan 11-05 owns
`app/api/checkout/route.ts` and the webhook route and does the call-site wiring. Plan 11-01
owns `.env.example`. Do not edit either file here.
</objective>

<uat_constraint priority="read-this-first">
## D-06a — testers will trigger sends they never receive. This is expected.

With no verified sending domain (deferred by D-09 and the phase scope fence), Resend's
`onboarding@resend.dev` sender **can only deliver to the email address the Resend account
itself is registered under.** Every other recipient — including every UAT tester — will see
the send succeed from the app's side and receive nothing.

Consequences that this plan hard-codes into its verification, rather than leaving to be
discovered mid-UAT (Pitfall 7):

1. **Verification of a real send is done in the Resend dashboard send log**
   (Resend -> Emails / Logs), **not** in anybody's inbox. A row appearing in that log with
   the right recipient and subject IS the pass condition.
2. **"The tester did not get the email" is not a bug.** It is the documented, accepted
   consequence of shipping on `*.vercel.app` without a domain. Do not open a defect for it,
   and do not spend time debugging deliverability.
3. **The owner is the only person who can eyeball the rendered email.** Task 3's checkpoint
   therefore asks the owner — not a tester — to look at the actual received message.
4. This constraint must be restated verbatim in the phase's UAT notes and in the pre-launch
   checklist (D-12), where "verify a sending domain" becomes a listed go-live item.
</uat_constraint>

    Apply UI-SPEC Contract 6 as hard constraints, because most email clients — Outlook desktop
    especially — support none of this project's normal styling:

    - Layout: React Email's `Html`, `Head`, `Preview`, `Body`, `Container`, `Section`, `Row`,
      `Column`, `Text`, `Heading`, `Link`, `Hr`, `Img` primitives only. These render to HTML

      Outlook.
    - Styling: inline `style` props only. No embedded stylesheet element, and no Tailwind
      utility classes — Tailwind's generated CSS does not exist in the rendered email HTML,

    - Fonts, and this is the part that surprises people: **Fraunces and Inter will not load in
      Gmail or Outlook.** Web fonts are broadly unsupported. Do not attempt to load them and
      do not name them first in the stack. Use the web-safe fallback chains that
      `tailwind.config.ts` already declares as its fallbacks:
      headings `Georgia, 'Times New Roman', serif`;
      body `-apple-system, BlinkMacSystemFont, 'Segoe UI', Helvetica, Arial, sans-serif`.

      sepia's contrast margin is too thin to risk in an environment nobody can QA per client.
    - Status: render `statusLabel` as bold text coloured with `statusColor`. Do not build a
      rounded pill with a background — background-colour support on inline elements is
      inconsistent across clients, and a bold coloured word survives everywhere a badge does not.
    - Width: a fixed 600px maximum content width, centred. Standard email convention.
    - Images: product thumbnails only if the line item carries one, each with explicit `width`,
      `height` and `alt` attributes. Many clients block remote images by default, so alt text
      is the actual fallback experience, not a nicety.
    - Preheader: a `Preview` element carrying `content.preheader`, so inbox previews show the
      order reference instead of raw markup or whitespace.
    - Order link: render a "View your order" link to `content.orderUrl` ONLY when it is
      non-null. When it is null, omit the link entirely — never substitute a default origin
      (D-09).
    - Interpolate every value as plain React children so it is escaped. Do not reach for
      React's raw-HTML injection escape hatch anywhere in this file.

    Then write `lib/email.ts`. Mirror `lib/stripe.ts` line for line in shape:

    read `process.env.RESEND_API_KEY` into a const; export a module-level client that is a new
    `Resend` instance when the key is present and `null` when it is not; export a boolean
    `emailEnabled` derived from the key, matching `stripeEnabled`'s role. An unset key must be
    an ordinary, expected, non-crashing state — the whole point of the idiom.

    `export async function sendOrderConfirmation(orderId: string): Promise<void>`:

    1. If the client is null, `console.warn` once with the order id only, and return. Never
       throw, and never include the key or any part of it in that message.
    2. Look the order up by id through `prisma.order.findUnique`. If there is no row, return
       quietly.
    3. Build content via `buildOrderConfirmationContent(order, process.env.NEXTAUTH_URL ?? null)`.
       Pass the env value straight through — no fallback origin, no default host string (D-09,
       and note Pitfall 4 where exactly this kind of fallback rotted in the checkout route).
    4. Render the React element once, and render its plain-text alternative from that same
       element using React Email's plain-text render option. Generating text from the same
       component is what makes drift structurally impossible — do not hand-write a second
       text template.
    5. Call `resend.emails.send` with `from` = `process.env.EMAIL_FROM`, `to` = the order row's
       own `email` column, `subject` = `content.subject`, plus the React element and the
       rendered text. **The recipient is derived solely from the looked-up row.** The function
       signature takes an order id and nothing else, so no caller can ever steer a receipt
       toward an address of its choosing — this is the mitigation for T-11-04-01, not an
       incidental design choice.
    6. Wrap the send in try/catch. On a thrown error or a returned error payload, report it
       with `console.error` carrying the order id and the error's name and message, then
       return normally. Log no request payload and no environment value. A mail outage must
       never propagate into the Stripe webhook, where an exception would turn into a Stripe
