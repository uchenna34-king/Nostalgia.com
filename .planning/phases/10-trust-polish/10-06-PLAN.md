<objective>
Deliver the owner-only review-moderation surface for the admin back-office: a `/admin/reviews` list of every review (including hidden ones) plus `hideReview` / `unhideReview` / `deleteReview` Server Actions, all gated by the Phase 9 `requireOwner()` reused verbatim. This is the "auto-publish with owner removal" half of D-02 — reviews go live immediately (10-05), and this plan is how the single store owner takes an abusive or off-brand review down.

Because the phase's read layer surfaces one canonical rating source (10-03 `lib/reviews.ts`, consumed by the PDP, product cards, and the Product JSON-LD), moderation is wired at that source: this plan introduces a `hidden` boolean on the `Review` model and filters it out of the storefront-facing reads, so a single "Hide" click removes a review from the list, the compact stars, the aggregate average/count, and the SEO structured data simultaneously — never a state where a hidden review still drags the average or appears in JSON-LD.

Purpose: give the owner a real removal control (TRST-01 / D-02) without an approval queue and without any customer report/flag flow.

Output: `prisma/schema.prisma` (the `hidden` column + a migration), `lib/reviews.ts` (storefront read filter), `app/admin/reviews/**` (list page + moderation actions), `components/admin/ReviewModerationTable.tsx` (the client table island), and the AdminNav "Reviews" link.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client -> review-moderation Server Actions | Untrusted HTTP input crosses here. `hideReview` / `unhideReview` / `deleteReview` are public POST endpoints callable directly with a valid session cookie, outside the rendered admin UI — the primary attack surface of this plan. |

| moderation action -> Prisma/SQLite | A validated single-row `update` (hide/unhide) or `delete` on `Review`, keyed by `id`. No cascade reaches `Order` (reviews have no order-history dependency). |
