<objective>
Deliver the order-management and fulfillment surface for Phase 9 (ADMN-04, D-11/D-12/D-13): an owner-gated admin orders list, a single-order detail view, and a validated fulfillment Server Action that advances `Order.status` through a fixed allow-list and sets an optional tracking number and notes.

Purpose: This is the last of the four ADMN requirements — the owner needs to see every customer order and move each one through a simple linear fulfillment pipeline (pending -> paid -> fulfilled -> cancelled) while hand-shipping. It introduces the project's allow-list-validation pattern for a customer-order *write* (previously the allow-list idiom was read-only, e.g. `buildOrderBy`), reusing the exact `Set`-based technique already proven in `lib/catalog.ts`.

Output: `lib/orders.ts` (the `ORDER_STATUSES` allow-list constant + `isValidOrderStatus` guard + a Prisma-free order-items parser), the `updateOrderFulfillment` Server Action, the orders list + order detail pages, the `OrderTable` and `FulfillmentForm` components, and a unit test proving the allow-list accepts only the four valid statuses.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client -> admin order Server Action (`updateOrderFulfillment`) | Untrusted input (status string, tracking, notes, orderId) crosses here. Server Actions are directly-callable public HTTP POST endpoints — a valid session cookie can invoke them via `curl`, bypassing the rendered admin UI entirely. This is the primary authorization + input-validation surface of the plan. |
| client -> admin order pages (`/admin/orders`, `/admin/orders/[id]`) | Read surface exposing customer PII (email) and order contents/totals. Page rendering is gated server-side by the 09-03 `app/admin/layout.tsx` `requireOwner()`; a non-owner must never receive any order data, including via `/admin/orders/[id]` id-guessing. |

## STRIDE Threat Register (ASVS L1 — block on high)

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-04 | Elevation of Privilege | `updateOrderFulfillment` Server Action | high | mitigate | `await requireOwner()` is the FIRST statement of the action (independent of the layout gate, which does not protect Server Actions per RESEARCH Pitfall 1). Non-owner/unauthenticated invocation is redirected/404'd before any Prisma write. Verified by the "requireOwner before any prisma. reference" acceptance grep. |
| T-09-05 | Tampering | `Order.status` write | high | mitigate | Incoming `status` is validated against the explicit `ORDER_STATUSES` allow-list via `isValidOrderStatus` (mirroring `buildOrderBy`/`SORT_OPTIONS`) and the action throws `invalid_status` BEFORE `prisma.order.update` — an out-of-set/forged value is never persisted. The UI `<select>` offers only the four values but is not the authority. Verified by `tests/orders.test.ts`. |
| T-09-06 | Information Disclosure | `/admin/orders` list + `/admin/orders/[id]` detail (customer email PII, totals) | high | mitigate | Both pages render only under the 09-03 admin layout `requireOwner()` gate; the detail route confirms owner access before returning ANY order, so IDOR by guessing an order id yields a 404-style block for non-owners. Single trusted owner legitimately sees all orders (D-11), so no per-user scoping is needed — but non-owner access to any order is blocked. |
| T-09-07 | Tampering | fulfillment action `data:` payload (mass assignment) | medium | mitigate | The action takes explicit typed arguments (orderId, status, trackingNumber, notes) and writes each field explicitly to `prisma.order.update({ data })` — no `FormData`/object spread, so a forged extra field cannot reach an unintended column (RESEARCH Pitfall 4). |
| T-09-SC | Tampering (supply chain) | npm installs | high | accept | No new packages are introduced this phase (RESEARCH "Package Legitimacy Audit" — table N/A, no `npm install`). The Package Legitimacy Gate does not apply. |
